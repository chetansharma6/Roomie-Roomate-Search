No duplicate columns with competing meanings are introduced. The distance column
retains the existing discovery contract; if the product needs separate preferred
maximum and actual listing distances later, add distinct fields deliberately.

src/types/profile.ts remains the canonical shared RoommateProfile interface.
src/types/database.ts re-exports it and adds ProfileRow, ProfileWrite,
RoommateRequestRow and UniversityDomainRow for raw database records.
The frontend-only src/types/RoommateProfile.ts demo type is preserved.

move_in_date may be NULL while a profile is a draft. The existing rowToProfile
mapper skips incomplete profiles until a move-in date is supplied. No fake date
is inserted. The additive preferences migration provides monthly_rent, room_type,
study_environment, guest_frequency, smoking and dealbreakers; all are optional.

The database derives university, university_id and verified_university_email
from auth.users and active university_domains. Client writes must omit these
columns and created_at/updated_at. Insert your own id plus writable fields;
updates may use only the ProfileWrite fields. This proves mailbox ownership
for an approved domain, not enrollment. Profile rows contain no email column.

RLS POLICY EXPLANATIONS

active_domains_read: authenticated users see active supported domains only;
students have no domain write privileges. Administrators manage the allowlist.

profiles_read: confirmed, supported university users see their own profile
(including inactive) and active profiles at the same university. Candidate
confirmation/domain status is checked live too. Anonymous users have no grant.

profiles_insert_own: the authenticated user can insert only their own id and
only with a confirmed supported email. A trigger derives verification and school.

profiles_update_own: only the owner with a currently verified supported email
can update. Column grants exclude identity, university, verification and timestamps.
The trigger guards ownership and maintains timestamps. No client delete policy.

requests_participants_read: only a sender or receiver who currently has a
confirmed supported university email can read a request.

requests_send_own: sender must be auth.uid(), status must start pending, and
both active profiles must be visible through profile RLS (same university).
Self-requests fail a CHECK; an unordered unique index prevents repeat requests
in either direction, even after a final decision.

requests_receiver_respond: only the receiver may update a pending request to
accepted or declined. Column grants allow status only. A trigger additionally
prevents identity/ownership/creation-time edits and changes to final decisions.
No client delete policy or cancellation/resend workflow is provided.

All application tables have RLS enabled. The legacy allowed_email_domains table
is retained, locked to clients and no longer used by the signup hook. The hook
now uses university_domains, avoiding two sources of authorization truth.
Private security-definer helpers use an empty search_path and never return email.

SERVER ADAPTER

api/_lib/supabase.ts uses the student's JWT and publishable key, so database
reads respect these policies. Auth rejects unconfirmed emails; the database
enforces approved domains and same-university access. Reads explicitly select
matching fields and require active profiles. No secret key is needed for this
adapter. Do not test RLS using a secret/service key, which bypasses RLS.
